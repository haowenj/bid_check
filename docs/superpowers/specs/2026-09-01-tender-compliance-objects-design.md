# 招标文件模板与编制材料提取重构设计

**日期：** 2026-09-01
**状态：** 已确认设计，待实现计划

## 目标

将当前“扫描招标文件并生成大量 `TenderRequirement`”的链路重构为面向后续模板比对的三类产物：

```text
招标文件
→ MinerU/现有结构解析
→ 功能区域识别
→ 完整投标模板
  + 少量项目专用编制要求
  + 少量模板外明确提交材料
```

本轮不实现投标文件真实解析、模板匹配、RAG、图片识别、签字盖章判断、实际合规判断或最终审查报告。

## 现状与问题

当前 `app/compliance_extraction.py` 的主链路是：解析 blocks → 按关键词选候选窗口 → 批量调用 LLM → 归一化成 `TenderRequirement`。确定性回退按候选窗口返回一条要求，LLM 也被要求把候选文本压缩成逐项自然语言规则；因此真实招标文件会产生几十条甚至 98 条要求，且模板正文被拆散为规则字段。

本次重构只改变提取产物与候选边界，不推倒现有基础设施：`StructuredBlock`、MinerU-compatible parser、解析缓存、结果缓存、来源 block 校验/修复、`ComplianceExtractionRecorder`、执行日志、workflow 并发和投标文件/审查 mock 服务继续复用。

## 方案

采用“确定性识别为主，LLM 窄范围辅助”的方案。

1. 解析器产出有序 `StructuredBlock`，保留 block id、类型、章节、顺序、文本和 MinerU metadata。
2. 程序根据标题语义识别功能区域，不使用固定章节号。
3. 在模板区域内根据标题、表格和表单/填写标记识别模板边界；同一个模板的连续 blocks 聚合为一个对象。
4. 在前附表区域内只选取影响投标文件组成、编制、填写、容量、提交形式、有效期、保证金和报价格式的行。
5. 在公告/资格相关区域内，只选取明确要求随投标文件提交的证明材料。
6. 根据项目专用要求生成明确的适用性约束，并过滤与其冲突的通用模板/材料。
7. LLM 只在程序无法确定时辅助模板边界、稳定名称、前附表相关行和“是否明确要求提交材料”的判断；模型不编译执行规则，不生成 `check_type`、`scope`、`evidence_type`、`checks` 等字段。

不采用“先生成 98 条再聚类”，因为它会继续把完整模板拆成自然语言要求；不采用“整份文件交给 LLM”，因为它会恢复大范围扫描、来源漂移和高调用成本。

## 结果接口

在 `app/models.py` 中增加轻量 `TypedDict`，不引入新的持久化领域模型。主提取结果为：

```python
{
    "templates": list[TenderTemplate],
    "project_requirements": list[ProjectRequirement],
    "supplemental_materials": list[SupplementalMaterial],
}
```

### 模板

每个真实模板是一个完整检查对象：

```python
{
    "id": "tender_template_001",
    "name": "法定代表人身份证明",
    "section": "商务投标文件格式",
    "block_ids": ["b0123", "b0124", "b0125"],
    "body": "模板中的连续正文",
    "tables": [
        {
            "block_id": "b0124",
            "text": "表格原文",
            "metadata": {"rows": 6}
        }
    ],
    "fields": ["姓名", "性别", "年龄", "职务", "投标人名称", "日期"],
    "attachments": ["身份证正反面"],
    "source": {
        "section": "商务投标文件格式",
        "block_ids": ["b0123", "b0124", "b0125"],
        "source_text": "上述 block 的完整原始文本"
    }
}
```

字段约束：

- `block_ids` 必须来自解析结果，按原文顺序排列；
- `body` 保留模板连续块的正文，不总结为规则；
- `tables` 保留表格 block 的原文和 metadata；
- `fields` 只记录从模板原文识别出的填写项，不预先规定如何检查；
- `attachments` 只记录模板中明确出现的附件/证明材料说明；
- `source` 作为统一追溯入口，`source_text` 必须由后端根据 block ids 回填，不能信任模型生成的来源文本；
- 跨多个连续 blocks 的模板只能生成一个对象。

### 项目专用编制要求

```python
{
    "id": "project_requirement_001",
    "requirement": "单个组成部分不得超过 50MB",
    "value": "50MB",
    "source": {
        "section": "投标人须知前附表",
        "block_ids": ["b0042"],
        "source_text": "原始行文本"
    }
}
```

这里只保存“要求是什么、项目具体值是什么、来源在哪里”。典型范围包括文件组成、分别编制、单项/总容量、清晰可读、扫描件、投标有效期、保证金适用性、备选方案、电子/纸质形式和报价小数位。不得把这些编译成执行类型或多条子规则。

### 补充证明材料

```python
{
    "id": "supplemental_material_001",
    "name": "营业执照",
    "material": "营业执照或事业单位法人证书复印件/扫描件",
    "source": {
        "section": "投标人资格要求",
        "block_ids": ["b0020", "b0021"],
        "source_text": "原始材料提交要求"
    }
}
```

只有“必须在投标文件中提供什么材料”进入本集合。营业执照/法人证书、分支机构授权、指定时间范围业绩证明、合同关键页、制造商登记证明及文件明确要求随投标文件提交的其他资格证明属于范围；“具有良好商业信誉”“具备丰富经验”“能够提供 7×24 小时服务”等资格条件本身不属于范围。

`TenderRequirement` 类型和旧函数名可以保留为导入兼容，但新主流程不再生成或返回 `TenderRequirement`，API/页面主结果不再提供 `requirements` 字段。

## 功能区域识别

标题匹配使用规范化文本（去空白、全半角差异和常见标点），结合 heading 类型、章节层级和原文顺序。不得依赖“第六章”等固定编号。

### 模板区域

识别以下语义及其同义变体：

- 投标文件格式
- 响应文件格式
- 投标文件组成
- 投标文件模板
- 资格审查文件格式
- 商务投标文件格式
- 技术投标文件格式
- 报价文件格式

区域开始于匹配标题，结束于同级/上级的新功能区域或文档结束。区域内的子标题、模板名称、表格、正文、附件说明和填写占位符按结构聚合。典型模板名称包括封面、投标函、法定代表人身份证明、授权委托书、廉洁承诺书、关联关系情况表、诉讼仲裁情况表、基本账户信息、业绩情况表、知识产权承诺函、安全承诺函、商务/技术/报价文件封面等。

模板边界优先由确定性结构判断：显式模板标题、新模板表格标题、明显的“（格式）/附件/表”等子标题以及连续的结构断点。相邻正文属于上一个模板时必须一并保留。仅当边界无法确定时，才向 LLM 发送同一功能区域内的有限候选块，并要求返回原 block ids 和分组，不要求生成规则摘要。

### 项目专用区域

识别以下标题及同义变体：

- 投标人须知前附表
- 投标须知前附表
- 项目专用条款
- 项目专用表
- 响应人须知前附表

从区域内提取与最终投标文件编制/组成/填写/形成/提交直接相关的行。评标办法、评分标准、评标委员会流程、招标代理流程和中标候选人规则不进入项目要求。

### 补充材料区域

在招标公告、资格条件、投标人资格要求、投标产品资格要求和制造商资格要求等语义区域搜索材料提交语句。候选必须同时满足：

- 出现提交动作或随投标文件语义，例如“提供”“提交”“附”“随投标文件”“作为资格证明”；
- 指向具体材料或证明，例如营业执照、授权、业绩证明、合同关键页、登记证明、证书或复印件/扫描件；
- 不属于履约阶段、服务过程、终验、人员管理、知识产权归属、违约责任或未来合同义务。

## 项目适用性

从项目专用编制要求中提取有限的适用性标记：

- `no_bid_bond`：明确无需投标保证金；
- `electronic_only`：明确只递交电子投标文件；
- `paper_copies_required`：明确要求纸质正本/副本；
- `alternative_bid_allowed`/`alternative_bid_disallowed`：明确备选方案适用性；
- 其他标记只在当前需求明确且能直接影响模板选择时添加。

适用性处理必须遵循项目专用信息优先：

- `no_bid_bond` 时，通用正文或模板区域中的投标保证金模板不进入 `templates`；
- `electronic_only` 且未明确要求纸质材料时，纸质正本、副本、密封包装、外层包封等不进入 `templates` 或 `project_requirements`；
- 只有存在明确项目专用信息时才过滤，不能根据常识推断；
- 被过滤的候选保存在 filter artifact 中，包含原 block ids、来源文本和过滤原因，便于复核。

## LLM 边界

将现有 LLM 适配器改为面向三类对象的窄结构输出。提示词只要求：

- 判断有限候选是否为模板及其连续 block 分组；
- 给模板生成稳定简短名称；
- 从前附表候选中挑选与投标文件编制直接有关的行并保留项目值；
- 判断资格材料候选是否明确要求随投标文件提交；
- 复制输入中的真实 block ids。

禁止模型：

- 把模板编译成自然语言 Requirement；
- 生成 `check_type`、`scope`、`evidence_type`、`checks`、`required_field` 等执行字段；
- 生成或修改 `source_text`；
- 扩展到整份文件、履约义务、评标评分或外部采购系统状态；
- 将一份模板拆为十几个检查规则。

无 LLM 配置时，确定性提取器仍基于标题、表格和原文占位符工作，保证有效 DOCX 不回退到固定五条 mock。配置 LLM 时，调用次数只随歧义区域增长，而不是随整份文档所有候选规则增长。

## 来源、缓存和 artifact

继续沿用已有来源机制：模型只能引用候选窗口中的 ids，后端验证 ids 存在并根据解析 blocks 回填 section/source text；错误来源在同一候选窗口内做确定性修复；无法修复则使 requirements stage 失败。三类对象都必须拥有可靠来源。

解析缓存继续使用现有独立的 MinerU/DOCX 解析缓存键和版本，保证 MinerU 结果复用。提取结果缓存版本升级为新的对象结果版本，缓存值从 `list[TenderRequirement]` 变为三类结果字典；缓存键仍包含解析器、LLM 配置、批次参数和文件内容哈希，不让旧 98 条结果遮蔽新链路。

任务级 `compliance_extraction/` 继续使用原子 JSON 和 append-only `execution.jsonl`。阶段 artifact 调整为：

- `01_parsed_blocks.json`
- `02_functional_regions.json`
- `03_templates.json`
- `04_project_requirements.json`
- `05_supplemental_materials.json`
- `06_filter_report.json`
- `07_result.json`
- `llm/call_NNN_input.json` / `llm/call_NNN_output.json`
- `summary.json`

summary 至少记录：模板数量、项目要求数量、补充材料数量、被过滤数量及原因、LLM 总调用/成功/失败/重试次数、每阶段耗时、总耗时、解析缓存命中和结果缓存命中。旧阶段文件若为兼容测试所需可以继续写入，但新主结果和文档必须以三类产物命名。

## Workflow/API/UI

`build_default_workflow` 的 requirements stage 调用新提取函数，bid parse 和 review 继续使用现有 mock。review mock 接收三类结果字典，不执行真实检查。非 DOCX 的历史字节桩可以保留兼容 fallback；真实 DOCX 解析/提取失败不得伪装成固定 mock。

任务 JSON 顶层保留原工作流状态字段和 `bid_parse`/`review_result`，提取结果改为：

```json
{
  "templates": [],
  "project_requirements": [],
  "supplemental_materials": []
}
```

结果页面分三组展示，并显示各自数量、模板完整内容/表格/填写项/附件和来源；页面不再使用“共提取 N 项合规性检查要求”的 Requirement 文案。

## 测试与验收

采用 TDD，先写失败测试再改生产代码。测试覆盖：

1. 不同章节编号下仍能识别模板/前附表功能区域；
2. 连续多个 blocks 的单个模板保持一个对象；
3. 模板正文、表格、填写项、附件说明和来源完整保留；
4. 模板不会被拆为多个自然语言 Requirement；
5. 前附表只保留文件组成、容量、清晰度、形式、有效期、保证金/备选方案和报价格式等编制要求；
6. 资格区域只补充明确要求提交的营业执照、业绩证明等材料；
7. 7×24 小时服务、终验、履约、人员管理、知识产权归属、评标评分和外部系统状态不进入三类结果；
8. “无需保证金”和“仅电子文件”能过滤冲突的通用模板；
9. 所有主结果来源 block ids 存在且 source text 由后端回填；
10. 解析缓存和结果缓存命中时不重复调用对应组件；
11. recorder 保留解析、区域、三类产物、LLM 调用、过滤报告、summary 和失败前中间结果；
12. API/workflow/UI 使用三类结果，bid parse/review 仍为 mock。

使用当前同一份真实招标文件重新运行并报告：

- 识别到的模板数量和名称列表；
- 项目专用编制要求数量；
- 补充证明材料数量；
- 至少数个典型模板的完整正文、表格、填写项、附件和来源；
- 相比原 98 条方案删除的内容类型；
- LLM 实际调用次数、失败/重试次数和耗时；
- 解析缓存与结果缓存命中情况；
- 过滤的保证金、纸质文件等通用候选及理由。

真实验收完成后停止，不继续开发后续投标文件检查能力。
