# 普通附件全量检查设计

## 目标

在已经验证的附件检查闭环上，将检查范围扩展到全部“已匹配且完整模板正文明确要求证明材料/附件”的普通模板，同时保持现有招标解析、投标解析、模板匹配、图片章节关联、附件检查提示词和结果校验不变。

## 范围与边界

- 检查输入包括完整招标模板 `body/source_text`、`attachments` 辅助信息、已匹配投标模块正文/表格和该模块章节关联的全部统一图片资产。
- 独立图片和表格 HTML 内嵌图片均通过结构化结果的章节关系进入检查器；不重新扫描整份投标文件。
- 普通材料包括模板正文明确要求随附的身份证明、资格证明、开户证明、授权证明、使用权证明及其他同类材料。
- `21` 以及 `21.1`～`21.6` 业绩材料属于明确排除的复杂附件范围，本轮不进入检查。
- 本轮不执行项目专用要求、文件大小、CA、加密、平台状态、真实性或业绩合同内部审查。

## 候选模板判定

新增一个通用、确定性的候选判定步骤，优先读取完整 `body` 与 `source.source_text`，合并去重后检查明确的材料要求语义，例如“应附”“应提供”“提供复印件/扫描件”“提供证明文件”“提供相关资料及证明”“提供使用权证明”等。`attachments` 仅作为辅助提示，不能替代完整模板正文，也不能让只有图片占位或纯文本模板进入视觉检查。

带有“如有”“若涉及”“如采用”“不涉及则无需提供”等条件的材料要求仍属于候选项，因为适用性需要结合投标模块正文判断。候选筛选器不因图片为空直接生成业务结论；模型继续使用完整模板和模块内容区分 `pass`、`fail` 与 `uncertain`。

候选项必须同时满足：模板与投标章节匹配成功、投标章节存在、模板不属于 21 业绩范围、正文存在普通材料要求。候选结果和最终附件结果都按招标模板原始顺序排列。

## 执行与结果

复用现有附件检查 system prompt、user prompt、JSON 结果结构、证据 image ID 校验、3 路并发、一次临时错误/超时重试和单项失败隔离。一个模板的所有关联图片组成一次检查调用；单项模型调用失败记录 `execution_status=failed`，不得混同为业务 `fail`。

每项结果继续保留 `template_id`、`template_name`、`bid_module_name`、`bid_section_id`、`image_ids`、`status`、`summary`、`materials`、`facts`、`requirements`、`evidence_image_ids` 和 `llm_elapsed_ms`，并通过 recorder 保留实际 prompt、图片路径/来源、表格来源、原始返回、结构化结果、耗时和重试记录。

## 页面

保留现有结果表，只移除“仅检查 3 类”的固定范围文案。参与附件检查的模板显示附件状态、材料类型、结论和证据图片数量，并允许查看具体 requirement/evidence；未进入附件检查的纯文本模板不显示为失败。

## 验收

测试覆盖通用正文判定、`attachments` 缺漏、纯文本/图片占位排除、条件性要求、21.x 排除、稳定顺序、并发隔离和正式结构化图片证据。额外使用临时输入覆盖：移除身份证一面应识别必要组成部分缺失；移除强制开户证明应识别材料缺失。真实结构化结果、图片资产和正式结果文件不作为负样本的修改对象。
