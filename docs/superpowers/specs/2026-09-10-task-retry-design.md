# 标书检查任务失败重试设计

## 1. 背景与目标

当前标书检查任务失败后只能查看错误，任务列表没有恢复入口。任务由多个有依赖关系的阶段组成，部分阶段已经成功生成的产物可以安全复用，因此需要支持人工选择：

- 从头开始：保留原任务和上传文件，重新执行该任务全部阶段；
- 从失败阶段开始：保留失败阶段之前已经成功的阶段，只重新执行失败阶段及其后续阶段。

重试发生在原任务上，不创建新任务，不改变任务 ID，也不删除原始上传文件。系统不增加自动重试；本需求只增加用户主动触发的手动重试。

## 2. 现状与约束

现有任务记录只有 `requirements`、`bid_parse`、`review` 三个阶段状态。全面校验在 `review` 后继续执行评标规则提取、客观评分、主观评分和否决规则，但这些环节目前没有独立状态；失败时只能把它们归类为 `review`。

现有阶段产物写入任务目录并采用稳定文件名，包括：

- 合规对象提取：`compliance_extraction/07_result.json` 及其细分产物；
- 投标文件解析：`bid_document_cleaning/structured_document.json`、`cleaning_summary.json` 等；
- 评标规则提取：`compliance_extraction/11_evaluation_rules.json`；
- 评标执行：`objective_scores.json`、`subjective_scores.json`、`veto_rule_reviews.json`。

已有代码已经支持基于文件哈希加载可复用投标文件证据，但工作流目前每次运行都从头调用服务，且只在较晚阶段把结果写入任务记录。重试必须补齐每个成功阶段的结果保存和加载边界。

## 3. 设计选择

### 3.1 原任务恢复

新增任务级重试入口，在数据库事务中校验任务当前状态必须为 `failed`，然后一次性完成以下操作：

1. 将任务状态设置为 `pending`，防止页面继续把旧任务视为失败；
2. 依据重试起点，将起点及其后续阶段状态置为 `pending`；
3. 保留起点之前的阶段状态和结果字段；
4. 清除起点及其后续阶段的旧结果字段，避免旧结果在新执行不完整时被误展示；
5. 保留所有上传文件和起点之前的阶段产物；起点及其后续阶段成功写入时覆盖对应产物；
6. 在执行日志中记录重试起点和原失败阶段。

“从头开始”会将该任务所有派生阶段结果重置，但不会删除上传文件。重试仍使用原任务目录和原任务 ID。

### 3.2 细化阶段模型

保留现有 `requirements_status`、`bid_parse_status`、`review_status` 字段以兼容当前接口和页面，同时新增以下独立状态字段：

- `evaluation_rules_status`：评标规则提取；
- `objective_scoring_status`：客观评分；
- `subjective_scoring_status`：主观评分；
- `veto_rule_execution_status`：否决规则执行。

逻辑阶段名称扩展为：

```text
requirements
bid_parse
review
evaluation_rules
objective_scoring
subjective_scoring
veto_rule_execution
```

其中 `review` 表示合规性检查。`failed_stage` 对新失败记录保存实际逻辑阶段；旧数据中的 `review` 仍按兼容逻辑读取。评标模式继续保留旧的 `requirements_status` 作为兼容别名，同时将它与 `evaluation_rules_status` 同步，避免已有调用方看到状态倒退。

任务的阶段执行顺序按检查模式确定：

```text
compliance: requirements + bid_parse（并行） → review
evaluation: evaluation_rules → objective_scoring → veto_rule_execution
full: requirements + bid_parse（并行） → review → evaluation_rules → objective_scoring → subjective_scoring → veto_rule_execution
```

按检查模式处理不适用阶段：`compliance` 任务的四个评标状态保持 `pending`；`evaluation` 任务不执行合规检查，新增的合规阶段状态不参与重试判断，旧的 `review_status` 继续保留现有终态以兼容旧页面；评标模式中不执行的主观评分状态保持 `pending`。详情页按任务模式把这些阶段显示为“本阶段跳过”，不额外执行不适用的服务。

### 3.3 产物复用边界

工作流在每个阶段成功后立即把可供后续阶段使用的结果写入任务 `result_json`，并继续写入现有阶段产物文件。重试从中间阶段开始时，优先从任务记录读取前置阶段结果；需要结构化文件证据的服务继续从其已校验哈希的阶段产物目录加载。

复用前必须检查前置阶段状态和最小产物是否存在：

- `requirements`：任务结果中的要求提取结果，或 `07_result.json`；
- `bid_parse`：任务结果中的解析结果及其结构化文档产物；
- `evaluation_rules`：任务结果中的规则提取结果，或 `11_evaluation_rules.json`；
- 评分和否决阶段：其依赖的评标规则、投标结构化文档及客观评分结果。

如果前置状态显示成功但产物缺失或哈希校验失败，“从失败阶段开始”返回冲突错误并提示用户改用“从头开始”。系统不会静默用缺失产物继续执行。

并行前置阶段的特殊规则：

- 只有 `requirements` 失败时，重试只执行 `requirements`，复用成功的 `bid_parse`；
- 只有 `bid_parse` 失败时，重试只执行 `bid_parse`，复用成功的 `requirements`；
- 两个前置阶段都失败时，从失败阶段开始会同时重试两个失败分支；
- 前置阶段成功、`review` 失败时，重试只执行 `review` 及全面校验的后续阶段。

### 3.4 工作流接口

将工作流入口扩展为可选重试起点：

```python
workflow.run(task_id, retry_from=None)
```

新建任务保持 `retry_from=None` 的现有行为。重试接口在数据库重置成功后以 `retry_from` 调用后台工作流。工作流根据检查模式和起点计算需要运行的阶段，并为每个跳过的成功阶段加载已保存结果，而不是再次调用服务。

每个实际阶段成功后都更新对应状态和结果字段；阶段失败时保存精确的 `failed_stage` 和错误信息。全面校验的评标阶段失败不再统一写成 `review`。

重试期间继续复用原有执行日志文件，并追加 `workflow.retry.start`、阶段开始/结束/失败和新的工作流结束事件。工作流汇总保留本次尝试的起点和状态，完整尝试轨迹以追加日志为准。

## 4. API 与页面

### 4.1 重试 API

新增：

```text
POST /api/bid-check/tasks/{task_id}/retry
```

请求体：

```json
{"retry_from": "start"}
```

或：

```json
{"retry_from": "failed_stage"}
```

接口行为：

- 任务不存在返回 `404`；
- 任务不是 `failed` 返回 `409`；
- 前置成功状态或产物无法复用返回 `409`，包含可读的修复提示；
- 成功重置并加入后台执行后返回 `202`，返回原任务的最新任务信息。

### 4.2 任务列表

失败任务行增加“重试”按钮，与“删除”并列。点击后打开重试弹窗：

- 默认选中“从失败阶段开始”；
- 显示精确失败阶段名称和“会复用之前成功阶段产物”的说明；
- 提供“从头开始”选项；
- 提交期间锁定选项和按钮，避免重复提交；
- 成功后刷新列表，任务进入等待/执行状态；
- 失败后显示 API 返回的错误，不移除任务行。

任务进入 `pending` 或 `running` 后，重试按钮禁用；完成任务不显示重试按钮，保持当前删除和结果查看行为不变。

任务详情页继续显示精确失败阶段和错误信息，进度卡片增加评标阶段状态，轮询逻辑覆盖新增状态字段。

## 5. 数据库迁移与兼容

SQLite 初始化逻辑需要支持已有数据库：启动时检查新增列并使用安全的 `ALTER TABLE ADD COLUMN` 补齐，随后按检查模式回填评标规则状态。原有三列和原有接口字段不删除。

重试状态重置必须在一个写锁和数据库事务内完成。条件更新只允许从 `failed` 进入 `pending`，避免两个请求同时获得重试资格。重置结果字段和阶段状态必须作为同一事务的一部分提交。

## 6. 错误处理与安全

- 只允许重试 `failed` 任务；正在运行、等待、已完成任务都不能通过该接口重试；
- 只操作当前任务目录内的已知派生产物，不删除原始上传文件；
- 所有产物路径继续通过现有任务目录边界校验；
- 阶段重试失败后任务回到 `failed`，并更新为本次实际失败阶段；
- 旧任务没有细化失败阶段时，按已有 `failed_stage` 映射到兼容阶段；若无法安全确定中间依赖，则拒绝“从失败阶段开始”，允许“从头开始”；
- 不返回内部堆栈、密钥或服务认证信息。

## 7. 测试与验收标准

采用测试驱动开发，先为每个行为写失败测试，再实现最小改动并运行完整测试集。

### 7.1 数据与工作流

- 保存要求提取、投标解析、合规检查和每个评标阶段的部分结果；
- 失败在每个细化阶段准确记录；
- 从 `requirements` 失败重试时不调用成功的 `bid_parse`；
- 从 `bid_parse` 失败重试时不调用成功的 `requirements`；
- 从 `review`、评标规则、客观评分、主观评分或否决规则失败重试时只执行该阶段及后续阶段；
- 两个并行阶段同时失败时两支都能重新执行；
- 前置产物缺失时拒绝中间重试；
- 重试失败后可以再次重试；
- 原任务 ID、上传文件和被复用产物路径不变。

### 7.2 API 与 UI

- 成功重试返回 `202`，任务状态进入 `pending`；
- 非失败任务、未知任务和无效重试选项返回明确错误；
- 任务列表失败项显示重试入口和失败阶段；
- 重试弹窗包含“从头开始”和“从失败阶段开始”两个选项，默认后者；
- 重试期间按钮状态正确更新；
- 详情页能显示新增评标阶段状态和精确失败阶段。

### 7.3 回归

运行完整 pytest 测试集，并检查现有创建、查询、删除、结果展示和评标模式行为没有回归。

## 8. 非目标

- 不创建新的任务记录或新的任务 ID；
- 不实现自动重试、定时重试或可配置重试次数；
- 不改变现有检查规则、评分规则或产物内容格式；
- 不引入通用 DAG 引擎或新的外部队列系统。
