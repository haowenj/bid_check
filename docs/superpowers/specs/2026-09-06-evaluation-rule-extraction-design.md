# 评标规则结构化提取设计

## 目标

在现有标书检查 Web 工作流中新增第一阶段“评标规则校验”能力：基于招标文件已有的 MinerU 结构化解析结果，完整定位评标相关章节，将评分规则和明确的否决性规则编译为可追溯的结构化数据，并写入独立产出物。

本阶段只处理招标文件中的规则本身，不使用投标文件内容执行评分、总分计算、排名、主观打分或实际否决判断。

## 范围与边界

纳入：

- 评标办法、评审办法、综合评估法、评分标准、初步评审、详细评审及其完整子章节；
- 商务、技术、服务、价格等评分大类及其评分表；
- 企业业绩、人员、资质证书、荣誉奖项、方案、售后、报价等具体评分项；
- 资格审查、符合性审查、否决投标、废标、无效投标等明确具有继续评审后果的规则；
- 与评分项或否决条款直接绑定的证明材料、时间/数量/金额/比例/上下限等条件；
- 表格关系无法可靠确认的原文，作为不确定规则保留，不强行编译。

排除：

- 投标文件实际得分、总分、排名和中标候选人计算；
- 对技术方案等主观项的模拟打分；
- 实际执行否决、废标或资格审查判断；
- 仅描述评标委员会组成、评标流程、开标流程、评标原则或法规引用而没有具体执行条件的内容；
- 投标模板正文、合同履约条款、技术需求等与具体评分/否决无直接关系的内容；
- 根据行业经验或法规补充招标文件未出现的规则。

## 设计方案

新增 `app/evaluation_rule_extraction.py`，与 `app/compliance_extraction.py` 并列。新模块复用以下稳定基础设施，但不复用合规提取器的功能区域过滤和三类合规对象 Schema：

- `MinerUDocumentParser` 与 `StructuredBlock`：获得带顺序、章节、表格元数据和真实 `block_id` 的低噪声文本；
- `JsonDocumentCache`：复用 MinerU 解析结果缓存；
- `ComplianceExtractionRecorder`：复用任务级原子 JSON 产出、LLM 输入/输出和 append-only 执行日志；
- OpenAI-compatible Chat Completions：复用现有无密钥的确定性 fallback、请求脱敏和错误处理约定。

### 章节定位与候选窗口

1. 从完整 `StructuredBlock` 序列中识别评标相关标题和明确否决标题。
2. 按标题层级和连续文档顺序建立完整章节窗口；窗口包含标题、所有子章节、表格、表格后紧邻的证明材料要求和上下文。
3. 评分表作为不可拆分单元保留；表格使用原始 HTML/表格元数据解析逻辑恢复行列，不把分值、评分标准和证明材料按相邻文本猜配。
4. 过滤目录、模板中的“评审索引表”、纯流程说明和没有具体评分/否决条件的内容，但将被过滤对象及原因记录到过滤报告。
5. 候选窗口总字符数、完整章节边界和实际发送字符数都写入 artifact。总量在模型预算内时整体一次提交；超出时只在完整评审章节或完整评分表边界切分。

### LLM 协议

模型只负责在候选窗口内理解和结构化，不负责补全文档之外的规则。输出只能包含以下集合：

```json
{
  "source_sections": [],
  "score_categories": [],
  "score_items": [],
  "veto_rules": [],
  "uncertain_rules": []
}
```

评分大类至少包含：

- `id`、`name`、`parent_id`、`full_score`；
- `original_rule`、`conditions`、`source_block_ids`；
- `structure_status`，用于标记明确或不确定的层级/分值关系。

具体评分项至少包含：

- `id`、`name`、`category_id`、`parent_item_id`；
- `original_rule`；
- `conditions`：时间、数量、金额、比例、范围、上下限和适用条件等；
- `scoring_method`：每项计分、分档、公式、扣分或其他原文计分方式；
- `full_score`；
- `evidence_requirements`：证明材料及特殊要求；
- `evaluation_type`：`objective`、`subjective` 或 `mixed`；
- `source_block_ids`。

否决性规则至少包含：

- `id`、`name`；
- `trigger_condition`、`consequence`；
- `evidence_requirements`；
- `original_rule`；
- `source_block_ids`。

不确定规则至少包含：

- `rule_type`、`description`、`original_rule`；
- `uncertainty_reason`；
- `source_block_ids`。

模型不得生成不存在的 `block_id`。后端校验来源 ID 必须来自候选窗口，并按原始块顺序重建 `source_text`。Schema 不通过、来源不可信或规则与来源文本无法对应时，不将其静默丢弃，而是记录失败/不确定信息并保留原始候选上下文。

### 客观/主观标记

- 明确的数量、金额、日期、比例、固定分值、上限/下限、公式或分档对应关系标记为 `objective`；
- “内容完整、针对性强、措施合理”等需评委判断的标准标记为 `subjective`；
- 同一项同时包含客观门槛和主观分档时标记为 `mixed`；
- 模型无法确认时标记为 `mixed` 或写入 `uncertain_rules`，不得把主观标准强行转换成确定性公式。

## 结果与产出物

继续使用任务目录下的 `compliance_extraction/`，新增：

- `10_evaluation_rule_candidates.json`：实际候选章节、完整窗口、裁剪前/后字符数和 block 范围；
- `11_evaluation_rules.json`：独立正式产出物，包含 Schema 版本、使用的评标章节、评分大类、具体评分项、否决性规则、不确定规则、来源和统计；
- `12_evaluation_filter_report.json`：目录、流程说明、无具体规则文本等过滤项及原因；
- `llm/call_NNN_input.json` 与 `llm/call_NNN_output.json`：沿用 recorder 保存每次实际调用的请求、原始响应、解析结果、耗时、finish reason、usage 和 schema 状态。

正式产物的 `stats` 至少记录：

- 解析器、解析来源、候选章节标题和 block 数；
- 原始文本字符数、候选文本字符数、实际 LLM prompt 字符数和 token（模型 usage 可用时记录，否则为 null）；
- LLM 总调用次数、成功/失败次数、重试次数、每次耗时、总耗时；
- 评分大类数、具体评分项数、否决规则数、不确定规则数；
- 客观、主观、混合评分项数量；
- 过滤数量和无法可靠结构化数量。

缓存必须同时区分解析器、LLM 模型、提示词版本、批次预算和新 Schema 版本，避免旧合规对象结果遮蔽评标规则结果。

## 工作流、API 与页面

- 现有 `evaluation` 模式从“开发中”变为可提交；`full` 继续保持不可提交。
- 仍沿用现有上传接口，接收招标文件和投标文件以兼容当前协议；评标模式只将招标文件送入评标规则提取，投标文件不参与评分或否决判断。
- 工作流增加评标提取分支，完成后直接保存 `evaluation_rules` 结果和独立 artifact，不调用现有合规 review 服务。
- 结果页在评标模式下展示：执行摘要、使用章节、评分大类/子项层级、评分条件与证明材料、客观/主观标记、否决性规则、不确定规则和来源 block；不展示“预计得分”“最终排名”或实际否决结论。
- 合规模式和 `full` 的现有行为保持不变；`full` 不因本阶段实现而自动执行评标提取。

## 错误处理

- MinerU 解析失败、候选结构无法建立或 LLM 调用最终失败时，任务失败并保留已写入的候选/解析 artifact 与失败摘要；不生成伪造规则。
- 单次 LLM 输出 Schema 或来源校验失败时，按现有重试约定处理；重试耗尽后任务失败，错误中包含阶段和原因。
- 字符预算不足时只允许在完整章节/完整评分表边界拆分；单个完整窗口超预算也不得截断，记录为需要人工处理的不确定候选。
- 规则含义不清、表格行列无法可靠关联或材料绑定不确定时，保留原文到 `uncertain_rules`，不猜测、不静默过滤。

## 测试与验收

自动化测试覆盖：

- 评标标题识别、章节连续性、目录/流程排除和完整子章节保留；
- 评分表行列、分值、评分标准和证明材料的完整窗口保留；
- 客观/主观/混合类型标记协议；
- 评分大类与子项父子关系、来源 block 校验和来源重建；
- 否决规则的触发条件/后果提取，以及普通提醒不被误提为否决规则；
- 不确定规则保留；
- 单次整体调用与按完整章节切分、LLM 调用计数/耗时、失败 artifact 保留和缓存版本隔离；
- `evaluation` API/UI 可执行，`full` 仍拒绝，合规模式回归不变。

完成代码验证后，使用当前项目已有真实招标文件运行一次，核对：定位章节、裁剪前后文本量、prompt 字符数/token、调用次数/每次耗时/总耗时、评分大类数、具体评分项数、否决规则数、客观/主观项、不确定项，以及每个表格的层级、分值、条件、证明材料和来源 block。

## 非目标

本设计不包含第二阶段的投标文件实际评分、客观得分计算、主观评分、总分排名、否决执行、投标文件专项检查结果复用或任何按评分项硬编码的业务判断。
